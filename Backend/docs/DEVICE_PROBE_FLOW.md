# Hardware probe → registration → automatic activation

## Server-generated identifiers

- `nodeCode` is generated by the backend when an Admin creates a Node (`NODE-001`, `NODE-002`, ...; tối thiểu 3 chữ số). The code is included in the provisioning claim response and used for that Node's MQTT topic and broker ACL. It is an identifier, not a credential.
- `deviceCode` is generated by the backend only after a positive probe ACK (`DEV-001`, `DEV-002`, ...; tối thiểu 3 chữ số). Do not enter it in the frontend form or send it in the probe request/ACK. The backend puts the assigned `deviceCode` into the configuration sent during provisioning.
- `requestId` correlates each probe request/ACK; `commandUuid` correlates commands/ACKs. These IDs are not MQTT credentials.

## What this changes

- `POST /api/devices/probe` (Admin only) publishes a probe request to the selected online Node and waits for a matching MQTT ACK. **No `devices` row is inserted** when the Node is offline, the timeout expires, the request identity mismatches, the self-test fails, or hardware feedback is invalid.
- `POST /api/devices` remains for compatibility, but calls the same probe-first controller. There is no direct unverified insert path.
- A positive probe creates `REGISTERED` with a backend-generated `deviceCode` and `presenceVerifiedAt`. The probe evidence is validated from the MQTT ACK in memory and is not duplicated into a device evidence column in MySQL.
- `REGISTERED → PROVISIONED` sends a new config version to the Node. The Node must ACK the exact version.
- A SENSOR becomes `ACTIVE` automatically only when the config version has been ACKed and fresh, valid, non-backfilled telemetry is received within five minutes.
- A PUMP becomes `ACTIVE` automatically only when the config version has been ACKed and the Node reports `deviceStatus: "READY"`, `ready: true`, and a positive current/flow feedback self-test matching the configured feedback type.
- Manual `PROVISIONED → ACTIVE` is rejected.

## Database change

For a database already created from the previous schema, back it up then run the simplification migration. It backfills `readinessType` from existing `readinessEvidence`, adds missing lifecycle timestamp columns when needed, and removes the redundant evidence columns. The script is safe to re-run on MySQL where `devices` already exists:

```bash
mysql -u root -p iot < database/migrations/20261027_simplify_device_evidence.sql
```

Replace `iot` with your DB name. For a fresh database, `database/smart_agri_mysql_demo.sql` already creates the new nullable columns.

## MQTT topics

Use the configured `MQTT_TOPIC_PREFIX` (default in `.env.example` is `iot`).

- Backend → Node: `{prefix}/{nodeCode}/device/probe`
- Node → backend: `{prefix}/{nodeCode}/device/probe/ack`
- Backend → Node: `{prefix}/{nodeCode}/config`
- Node → backend: `{prefix}/{nodeCode}/config/ack`
- Sensor readings: `{prefix}/{nodeCode}/telemetry`
- Pump readiness proof after applying config: `{prefix}/{nodeCode}/status`

### Probe request: SENSOR

```json
{
  "requestId": "<UUID>",
  "action": "PROBE",
  "type": "SENSOR",
  "gpioPin": 34,
  "hardwareFeedback": null,
  "allowActuatorTest": false
}
```

The ACK must echo `requestId`, `detectedType`, and `gpioPin`. There is intentionally no `deviceCode` yet: the backend generates it only after a successful probe. The incoming MQTT ACK may include `presenceEvidence`/`selfTest.evidence` as a transient protocol field for validating the probe, but Backend does not persist that verbose string in `devices` or the audit payload. The device row stores only `presenceVerifiedAt`. A sensor is accepted only when `present: true`, `selfTest.ok: true`, and `selfTest` contains a supported `metric` and finite `value` read from the actual sensor driver. Do not report a hardcoded value as a successful hardware test.

```json
{
  "requestId": "<same UUID>",
  "detectedType": "SENSOR",
  "gpioPin": 34,
  "present": true,
  "presenceEvidence": "SENSOR_READ:SOIL_MOISTURE",
  "selfTest": { "ok": true, "metric": "SOIL_MOISTURE", "value": 42.5 },
  "firmwareVersion": "1.2.0"
}
```

### Probe request: PUMP

A plain ESP32 GPIO or relay output cannot prove that a physical pump is connected. The form therefore requires a current or flow feedback channel and explicit operator consent for a bounded test. The firmware must turn the output OFF in all paths, run no longer than 1,000 ms, and be adapted to the actual relay polarity/current/flow sensor. Ensure the pump is primed and it is safe to test before consenting.

```json
{
  "requestId": "<UUID>",
  "action": "PROBE",
  "type": "PUMP",
  "gpioPin": 26,
  "hardwareFeedback": { "type": "CURRENT_SENSOR", "gpioPin": 34 },
  "allowActuatorTest": true
}
```

The ACK also needs `present: true`, matching request identity, `presenceEvidence: "CURRENT_SENSOR"` (or `FLOW_SENSOR`), a positive `selfTest.value`, and `testDurationMs` from 1 to 1,000.

### Config ACK and activation

The Node should publish the config ACK only after it actually applies the requested configuration:

```json
{ "deviceCode": "DEV-<generated-code>", "version": 1, "success": true }
```

The existing backend code tracks the version; add `success: true` in firmware and only ACK when `success` is true. For a pump, after applying config, report a hardware readiness proof (must match the configured feedback type):

```json
{
  "deviceCode": "DEV-<generated-code>",
  "deviceStatus": "READY",
  "ready": true,
  "testedAt": "2026-10-27T04:00:00.000Z",
  "testDurationMs": 500,
  "presenceEvidence": "CURRENT_SENSOR",
  "selfTest": { "ok": true, "metric": "CURRENT_A", "value": 0.42, "evidence": "CURRENT_SENSOR" }
}
```

The readiness pulse must obey the same safety limits as the discovery test, and the status payload must include `testedAt` (ISO time) and `testDurationMs` (1–1,000). A stale or unbounded test is rejected. When fresh ready evidence and config ACK have both been accepted, the backend changes the device to `ACTIVE` and emits `device:update` over Socket.IO.

## MQTT ACL

Limit publication to a Node's own subtree. For each generated Node code (for example `NODE-001`), scope the ACL to that exact code. A Node should publish only to its own `{prefix}/{nodeCode}/#` subtree and subscribe only to its own command, config and probe topics. The backend needs subscribe rights to `iot/+/device/probe/ack` and publish rights to `iot/+/device/probe`, plus its existing command/config and telemetry subscriptions. Also use broker credentials; request IDs correlate messages but do not replace MQTT authentication/ACL.

## Important integration note

The Frontend + Backend package does not include firmware. The firmware maintainer must implement this payload contract on the real ESP32 driver: the probe request/ACK intentionally has no `deviceCode`, because the backend creates that code only after a valid probe. The backend cannot physically discover hardware by itself. Use actual sensor/relay/current/flow drivers; never return a hardcoded successful reading. Update Mosquitto ACL with the generated `nodeCode` before the Node connects.
